Introduction

Simple Theme Options registers a Theme Settings WordPress admin experience: nested sidebar, SPA-style section switching, one options form, responsive controls, composite fields (Tabs, Accordion, Group), conditional required visibility, and header quick search.

This guide is for developers, agencies, and product teams who ship client sites or bundle STO in a commercial theme. Samples use the SimpleThemeOptions\ namespace and text domain 'simple-theme-options'. It focuses on your sidebar and field PHP under includes/Admin/Sample/; core plugin bootstrap is documented in README.md.

License & resale

GPL v2 or later applies to this plugin’s PHP. When you resell or bundle, include license terms for your layer (theme, config UI, support). Keep GPL headers in shipped PHP. Point customers to this file and to README.md for integration depth.

  • White-label: Replace Sample\ menu and sections with your brand; adjust menu title and icon in Menu::register().
  • Post editor metabox: Optional 'metabox' / 'enable_metabox' on Options\Menu::register(); per-post meta _sto_theme_settings_post saves on Publish / Update (no separate save button). Filter sto_theme_settings_metabox_ui_enabled to hide metaboxes site-wide.
  • Support scope: In your own README, separate “STO core behaviour” from “your custom field classes” so buyers know what you maintain.

Requirements

  • WordPress 5.8+
  • PHP 7.4+
  • manage_options for Theme Settings

Quick start

  1. Activate the plugin.
  2. Add or change sidebar rows in includes/Admin/Sample/Sections.php so each screen you need exists as a leaf slug (§2).
  3. Add includes/Admin/Sample/Fields/{Name}/{Name}.php (PascalCase folder + filename = class name). In init(), call field APIs then Foo::instance()->register() / register_many() with 'section_slug' equal to that leaf (§1.1 PHP, §6.0).
  4. Optional: rename the Theme Settings menu in includes/Admin/Sample/Menu.php (register_menu()).
  5. Open Theme Settings in wp-admin (admin.php?page=theme-settings&section=…).

Customize

  • Navigation: add_section / add_sub_section — §2.
  • New field types: Singleton + register(), render, sanitize, and (when adding a type) document sto_render_section_content priority — §5 and README.md.
  • Styling: Scoped under .sto-option-panel-wrapper — see plugin assets/admin/css.

1. Overview

Theme Settings is one admin page. Each navigable panel is a leaf (section query arg). Fields register with section_slug equal to that leaf.

Golden rule Match 'section_slug' on every field to a leaf slug from your sidebar tree. To add a screen: register it in includes/Admin/Sample/Sections.php (add_section / add_sub_section — §2). To add fields: create includes/Admin/Sample/Fields/{Name}/{Name}.php with a singleton class (filename = class name, PascalCase). In init(), boot any field-type singletons you need, then call register() / register_many(). You do not need add_action( 'sto_include_option_fields', … ) for ordinary lists — the plugin queues early register() calls until that hook (FieldRegistrationDeferral).

Custom fonts: on Tools → Simple Backup, open the Custom fonts sidebar section (section=custom-fonts); on the in-menu Advance leaf, the Custom fonts card (CustomFontsAdmin). The user drags and drops or browses for a font file (WOFF2, WOFF, TTF, OTF, EOT) or a ZIP in the dashed drop zone (same pattern as the import JSON dropzone), or picks an existing file from the media library. Family name, weight, style, and category are auto-detected by FontFileMetadata from each font’s name + OS/2 tables (TTF/OTF/WOFF parsed inline; WOFF2 needs PHP brotli when available, else filename heuristics). For ZIP uploads, FontZipExtractor scans every entry in the archive (any subfolder), finds files with font extensions, extracts them to a temp folder, and previews or imports each face. Non-font ZIP entries are ignored. The card shows detected metadata (table for multi-font ZIPs) before save; click Add font / Add N fonts to commit. A Live preview block (family + style selects and sample text, like Typography fields) appears after upload: it previews pending faces from the current file/ZIP via live_preview on preview AJAX (ZIP fonts are served from a short-lived transient through sto_custom_fonts_serve_preview_font), then switches to imported fonts from CustomFontsRegistry::get_live_preview_data() after save. Each face is one table row with a checkbox; use Delete selected (or the row Delete link) to remove one or many faces from sto_custom_fonts and Typography pickers. Uploading a font with the same family, weight, and style as an existing face (or a duplicate inside the same ZIP) shows a replace confirmation before import; confirming replaces the previous face. Families merge into TypographyFontsCatalog (labelled Custom). Theme helpers: sto_get_custom_fonts(), sto_get_custom_fonts_css(). Front-end @font-face on wp_enqueue_scripts. AJAX: sto_custom_fonts_upload, sto_custom_fonts_preview, sto_custom_fonts_add, sto_custom_fonts_delete, sto_custom_fonts_serve_preview_font.

Demo mode: Options\Menu::register( …, array( 'demo' => false ) ) forbids the packaged sample sections and hides the Advance Demo mode switch on client menus. The packaged sample menu uses 'packaged_demo' => true: enable or disable the demo from Tools → Simple Backup (Demo mode card); while off, the top-level Theme Settings menu and toolbar quick links are hidden (direct admin.php?page=theme-settings redirects to the backup screen). Legacy bookmark options-general.php?page=sto-packaged-theme-settings-demo redirects there too. When demo is true and the menu is not packaged, samples stay off until option sto_theme_settings_ui_demo_enabled is on — toggled from Advance. SampleFieldModules::boot() always loads discovered field modules first, then calls Sections::register_without_demo() when Options\Menu::is_demo_mode_enabled() is false or Sections::register() when it is true; filter sto_theme_settings_demo_mode applies to that combined result.

Reading options in themes

includes/functions.php loads global helpers whenever the plugin is active. sto_get_option( 'field_id', $default ) returns one saved Theme Settings field by its registered id (stored under sto_options['field_id']) — same idea as Redux-style get( 'opt_name', 'field_key' ), except STO uses a single flat sto_options map, so you only pass the field key. Missing keys return your default.

sto_option_is_on( 'switcher_id', false ) is true when the stored value is one of 1, true, on, yes (typical switcher / checkbox tiles).

sto_color_field_background_css( 'color_field_id', '#ffffff' ) and sto_color_string_to_background_css( $stored, '#ffffff' ) normalize Color values to comma rgb() / rgba() for inline style="background-color: …" with esc_attr().

For responsive fields, sto_get_option() returns the full breakpoint map — use sto_get_responsive_option( $id, $viewport_width, $default ) to resolve one slice (see §3 Responsive and README.md). Full map helpers such as sto_get_options(), sto_get_effective_options_for_post(), etc. remain for advanced use.

In Theme Settings admin, alpha-enabled Color rows use wp-color-picker-alpha with data-alpha-color-type="octohex" so saves stay #RRGGBBAA; default vendor hex alone collapses alpha.

Always guard with function_exists( 'sto_get_option' ) if your theme template must tolerate the plugin being deactivated.

3. Responsive — how it works

3.1 Turning responsive on

Add 'responsive' => true (or a non-empty array — array only opts in; use 'device' for the tab list). Storage becomes a map of breakpoint => value under the same option id.

3.2 Default device tabs

If you omit device, the admin shows the default trio: xxl (desktop), md (tablet), mobile. If you pass 'device' => array( 'lg', 'md' ), the UI merges with the default set (deduped, canonical order).

3.3 HTML name attributes (scalar example)

Non-responsive select: name="sto_options[my_setting]". Responsive select: name="sto_options[my_setting][xxl]", [md], [mobile] (only keys for shown tabs).

3.4 Conditional required uses the eval breakpoint, not the visible tab

Each responsive row gets data-sto-require-eval-bp (default xxl). JS getOptionFieldValue( key, '' ) and PHP RequiredVisibility read that slice so show/hide does not flicker when you switch device tabs.

4.3 Whole group visibility

Pass 'required' at the root of Group::register( array( … ) ) — same schema. Inner fields can also have their own required.

4.4 HTML5 required vs conditional required

Conditional visibility uses the required array / JSON above. HTML5 mandatory inputs use 'html_required' => true on Input only — different feature; inactive leaf fieldset disabled avoids cross-panel HTML5 blocking.

Cross-panel dependencies main.js findOptionInputsByName prefers the active .sto-option-panel-section.sto-is-active, then falls back to the whole .sto-options-form, so a dependency in another leaf can still drive visibility when that input exists in the DOM (disabled fieldsets may still expose values for reads — test your combination).

5. Save, validation & adding a brand-new field type

  • One form #sto-theme-settings-options-form; inactive leaf panels use <fieldset disabled> so HTML5 required on another leaf does not block save.
  • Menu::maybe_handle_save_request() only updates keys registered for the current leaf; implement get_field_ids_for_section( $section_slug ) on your field class.
  • New field type checklist: FieldTitle for labels, data-sto-required when using rules, responsive contract (§9 in .mdc), getOptionFieldValue support in main.js, enqueue + init hooks, README.md + rules + this HTML.
